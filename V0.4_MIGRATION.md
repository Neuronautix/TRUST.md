# Proposed migration from TRUST.md v0.3 to v0.4

This document defines the explicit migration contract to be implemented for
v0.4. It does not change validation of a declaration that continues to declare
`trust_md_version: "0.3"`.

Migration is user-directed and may require information that v0.3 did not
record. A tool MUST NOT invent identifiers, protocol versions, evidence-basis
links, purposes, assessors, independence, or scientific conclusions. When a
required v0.4 fact is unavailable, migration MUST stop with an actionable
diagnostic or produce a clearly incomplete draft that is not represented as a
conforming v0.4 declaration.

## Migration procedure

1. Preserve the source v0.3 declaration unchanged and record its immutable
   location or digest.
2. Construct the required `subjects` registry. Identify the assessed v0.3 unit
   using an authoritative identifier plus either a version or immutable
   snapshot and digest.
3. If v0.3 has no `assessment`, use an empty `assessments` collection. Do not
   invent one.
4. If v0.3 has one `assessment`, create one v0.4 assessment and obtain its
   stable `series_id`, immutable version-specific `id`, and `version`.
5. Replace the embedded unit description with a `subject` reference.
6. Convert the protocol string only after supplying a protocol identifier and
   version. Preserve non-identifying legacy prose as migration metadata.
7. Move review status from `dimensions.review_status`, where present, into
   assessment provenance. Do not silently resolve conflicting v0.3 review
   declarations.
8. Link at least one inspectable `evidence_basis` record when the migrated
   assessment is active and reviewed. Do not downgrade review status merely to
   make the record validate.
9. Convert `assessment.date` to `assessed_at` as described below.
10. Set lifecycle state and append-only relations without changing the subject.
11. Validate under the v0.4 schema only after all required facts are supplied.

## Field-level mapping

| v0.3 source | v0.4 treatment |
|---|---|
| `trust_md_version: "0.3"` | Set to `"0.4"` only when the new contract is complete |
| `canonical` and assessed repository | Use to help construct `subjects[0].identifier`; add a repository version or immutable snapshot/digest |
| `assessment.unit` | Map to `subjects[].type`; the assessment refers to that entry through `subject` |
| no `assessment` | Preserve as zero assessments; still create the required subject registry |
| singular `assessment` | Map to one item in plural `assessments`; do not create additional interpretations |
| no assessment identity | User supplies `series_id`, immutable version-specific `id`, and `version` |
| `assessment.protocol` string | Split into `protocol.identifier` and `protocol.version`; preserve leftover prose as migration metadata |
| `assessment.date: YYYY-MM-DD` | Serialize as `assessed_at: YYYY-MM-DDT00:00:00Z` plus `assessed_at_precision: date`; the anchor does not assert a midnight event |
| `assessment.review_status` | Retain as assessment provenance |
| `epistemic_model.dimensions.review_status` | Remove from dimensions; compare with assessment provenance and require user resolution if inconsistent |
| `assessment.assessed_by` | Retain human and agent records; do not promote agent-only work to human review |
| `assessment.independent_review: true` | Map to `independence: declared-independent`; this remains a declaration, not verification |
| absent or false `independent_review` | Map to `independence: not-declared` unless the publisher explicitly declares another state |
| no `evidence_basis` | User supplies inspectable basis links for every active reviewed assessment |
| no purpose | Leave `purpose` absent for descriptive assessments; require it before adding fitness-for-purpose |
| no lifecycle state | Use `active` only when the publisher confirms the assessment is current |
| `assessment.supersedes` | Resolve to an immutable assessment-version ID in the same series; reject ambiguity or cycles |
| `dimensions.evidence_support` | Retain the same value and missing-state distinction |
| `dimensions.calibration` | Retain the same value and missing-state distinction |
| `dimensions.source_integrity` | Retain the same value and missing-state distinction |
| absent dimension | Keep absent; do not convert to an assessed-low or explicit missing state |
| `not-assessed` / `not-applicable` | Preserve exactly |
| lowest ordinary dimension value | Preserve as an assessment result, never as missing data |
| optional numeric refinement | Preserve only as non-probabilistic, assessment-scoped information |
| `corpus.average_trust` | Keep only as deprecated migration metadata; do not map to a v0.4 assessment aggregate |
| `corpus.band_distribution` / `median_band` | May be retained only in the scope of the single migrated assessment when their population and protocol remain explicit |
| impact or reuse extensions | Retain as impact metadata; never map into dimensions or fitness conclusions |
| unknown fields | Preserve as extensions where safe and emit notices; never silently drop them |

## Required user-supplied information

A formerly reviewed v0.3 assessment will normally need all of the following
before it can conform to v0.4:

- immutable subject identity information;
- assessment `series_id`, version-specific `id`, and `version`;
- protocol identifier and version;
- one or more inspectable evidence-basis links;
- confirmed lifecycle state; and
- an explicit independence declaration when one is intended.

Fitness-for-purpose is never inferred. Adding it also requires a declared
purpose and one standardized conclusion.

## Compatibility and round-trip expectations

Migration does not alter or invalidate the v0.3 source. Frozen v0.1–v0.3
schemas remain authoritative for their versions. A v0.4-to-v0.3 projection is
necessarily lossy when there are multiple subjects or assessments, lifecycle
versions, purposes, fitness conclusions, or basis links; tooling MUST disclose
that loss and MUST NOT overwrite the source.

Migration fixtures will include the unchanged v0.3 input and its explicit v0.4
result. Round trips must preserve strings, identifiers, datetime precision,
missing-state distinctions, assessor types, and extension values without type
loss.
